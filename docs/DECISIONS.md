# План архітектури QA Deck

Це поточний технічний план. Він може змінюватися, коли почнеться робота над окремими частинами системи.

## 1. Product - центральна сутність

Усі Resources, Plugin Configurations, profiles і Operation Logs належать до конкретного Product. Product описує програму або систему, яку тестують, і зберігає контекст для роботи з її середовищем.

## 2. Плагіни надають універсальні можливості

Plugin реалізує загальні Actions, наприклад роботу з файлами, Registry, логами або Jira. `Plugin Configuration` прив’язує ці можливості до конкретного Product. Так один плагін можна використовувати з різними продуктами й різними settings.

## 3. Resources та Actions утворюють спільну модель

Resource описує файл, setting, Registry key, лог або інший артефакт Product. Action описує одну операцію плагіна над такими ресурсами. Це дає спільну основу для profiles, Change Plan та історії операцій.

## 4. Моделі стану та переносима конфігурація розділені

Snapshot зберігає історичний стан, а Environment Profile описує бажаний стан.
Загальне керування станом через Workflow не продовжувалося, оскільки воно
повторювало б ці моделі. Product Setup вирішує іншу задачу: переносить
конфігурацію Product і плагінів між інсталяціями QA Deck. Майбутня оркестрація
має координувати дії, а не створювати ще одну модель стану.

## 5. Зміни мають бути передбачуваними

Перед внесенням змін плагін формує Change Plan із діями та рівнями ризику. Ризиковані операції потребують підтвердження. Помилка плагіна завершує лише його операцію й не повинна зупиняти QA Deck.

## 6. Snapshot, diff і Jira доповнюють основні сценарії

Snapshots фіксують стан Product, diff порівнює стани, а майбутня Jira
Integration має передавати діагностичні дані. Ці можливості доповнюють основний
сценарій QA Deck: підготовку, перемикання, відновлення та діагностику середовища.

## 7. Ядро залишається простим

Ядро будується на Python і Flask application factory та не містить
Windows-залежностей. Зараз QA Deck явно виявляє вбудовані плагіни й може
реєструвати передані plugin factories. Python entry points залишаються майбутнім
напрямом для зовнішніх встановлених плагінів. `pytest` перевіряє код QA Deck.
Чутливі дані не повинні потрапляти до snapshots або Operation Logs.
