# План архітектури QA Deck

Це поточний технічний план. Він може змінюватися, коли почнеться робота над окремими частинами системи.

## 1. Product — центральна сутність

Усі Resources, Plugin Configurations, profiles, workflows і Operation Logs належать до конкретного Product. Product описує програму або систему, яку тестують, і зберігає контекст для роботи з її середовищем.

## 2. Плагіни надають універсальні можливості

Plugin реалізує загальні Actions, наприклад роботу з файлами, Registry, логами або Jira. `Plugin Configuration` прив’язує ці можливості до конкретного Product. Так один плагін можна використовувати з різними продуктами й різними settings.

## 3. Resources та Actions утворюють спільну модель

Resource описує файл, setting, Registry key, лог або інший артефакт Product. Action описує одну операцію плагіна над такими ресурсами. Це дає спільну основу для profiles, workflows, Change Plan та історії операцій.

## 4. Profiles і workflows додаються поступово

Environment Profile або Preset зберігає потрібний стан Product, а Workflow / Setup задає послідовність Plugin Actions. Базові моделі варто додавати окремими невеликими кроками, а не реалізовувати весь сценарій одразу.

## 5. Зміни мають бути передбачуваними

Перед внесенням змін плагін формує Change Plan із діями та рівнями ризику. Ризиковані операції потребують підтвердження. Помилка плагіна завершує лише його операцію й не повинна зупиняти QA Deck.

## 6. Snapshot, diff і Jira доповнюють основні сценарії

Snapshots фіксують стан Product, diff порівнює стани, а Jira Integration передає діагностичні дані. Ці можливості корисні, але основний сценарій QA Deck — підготовка, перемикання, відновлення та діагностика середовища.

## 7. Ядро залишається простим

Ядро будується на Python і Flask application factory та не містить Windows-залежностей. Встановлені плагіни підключаються через entry points, а локальні — через механізм для розробки. `pytest` перевіряє код QA Deck. Чутливі дані не повинні потрапляти до snapshots або Operation Logs.
